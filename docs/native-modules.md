## 1. 我们要解决什么问题

全球能源市场往链上搬，长期卡在三件事：

| 痛点 | 现状 | EnergyChain 的解法（一句话） |
|---|---|---|
| **数据不互信** | 装机出力、电表读数、碳排因子由不同主体上报，互相不认账，靠人工对账 | 设备级签名 + 多源喂价聚合 + 可罚没的数据提供者 |
| **资产形态割裂** | 绿证、碳配额、PPA 收益权、储能资产份额各成孤岛，跨平台流转必须线下确权 | 统一的资产层：EAC / 碳 / RWA / 稳定币原生类型，全部走相同的合规通道 |
| **结算非原子** | 现金、绿证、碳、衍生品在不同系统，无法做到"一手交钱一手交证" | 链上多边净额清算，资产移交、对价、绿证 retire 三者在同一笔交易内完成 |
| **监管与隐私冲突** | 工商业用户不愿明文披露 MWh，监管又必须查得到 | 链上只放承诺值，监管节点持视图密钥可解明文 |
| **跨司法辖区** | 同一份资产在欧、美、亚的合规要求不一，硬编码做不下去 | 把"司法辖区"做成策略 DSL 的一个参数，可治理升级 |

**目标：让一度电从产生到消费的全过程在链上可追溯、可结算、可监管。**

## 2. EnergyChain 的定位

一句话：**面向全球能源结算场景的应用专用 L1 公链。**

- **应用专用**：不是通用 L1，所有原生能力都围绕"能源数据 + 能源资产 + 能源结算"展开。
- **全球结算**：默认面向 GO（欧）/ I-REC（国际）/ REC（美）/ LGC（澳）/ J-Credit（日）/ GEC（中）等多种证书体系；碳市场覆盖 EUA、CCA、Verra、Gold Standard、Article 6.4。
- **EVM 一等公民**：所有原生模块同时暴露 Cosmos Msg/Query 与 EVM Precompile，Solidity 合约可以直接调用。
- **可监管**：身份、审计、视图密钥、报告导出全部内置，监管方可作为只读节点接入。
- **不绑定国密**：国密 SM2/SM3 仅作为可选 verifier 插件，核心栈用通用密码原语（secp256k1/ed25519/keccak256/sha256）。

EnergyChain **不做** 的事：

- 不做通用 DeFi 公链（虽然 EVM 兼容，但定位不是这个）。
- 不做内置法币入金（链下 KYC/AML 由各 Issuer 完成，链上只校验凭证）。
- 不做 PoW、不做超低 TPS 链（共识层用 CometBFT BFT，1 秒出块）。

## 3. 整体架构（七层）

```
       ┌─────────────────────────────────────────────────────────────┐
   7   │  合规与治理层   policy · sanctions · mrv · dispute · dataslash │
       ├─────────────────────────────────────────────────────────────┤
   6   │  结算与支付层   clearing · escrow · streampay · scheduler     │
       ├─────────────────────────────────────────────────────────────┤
   5   │  市场层         market · auction · contract                  │
       ├─────────────────────────────────────────────────────────────┤
   4   │  资产层         eac · carbon · cfe247 · rwa · stablecoin      │
       ├─────────────────────────────────────────────────────────────┤
   3   │  数据可信层     oracle · meter                                │
       ├─────────────────────────────────────────────────────────────┤
   2   │  身份层         did · device · audit                          │
       ├─────────────────────────────────────────────────────────────┤
   1   │  基础链        Cosmos SDK + Cosmos EVM + IBC + 双角色 Staking  │
       └─────────────────────────────────────────────────────────────┘
```

阅读顺序的建议：**自下而上**。下层是基础设施，上层依赖下层。例如没有"身份"和"数据可信"，"资产"层就发不出可信的绿证；没有"资产"层，"市场"层无可交易标的。

## 4. 模块功能清单

每个模块按统一三段式描述：**解决什么 → 关键能力 → 与谁协作**。

### 身份层

#### 4.1 `did` —— 主体身份与可验证凭证

**解决什么**
能源市场上一切动作（发电、卖电、签发绿证、买碳）都必须能追到一个有据可查的法人或自然人。传统做法是各平台各建一套账号，跨平台必须重新 KYC。

**关键能力**
- 链上身份文档（DID Document）：公钥、控制权、服务端点、时间戳、是否注销。
- 多曲线密钥：默认 secp256k1 / ed25519，可挂 P-256 / BLS，国密 SM2 作为可选插件。
- 密钥轮换、控制权转移、注销，全部链上可证。
- 可验证凭证（VC）引擎：受信发证方颁发"已完成 KYC""已注册为 I-REC 签发方""已通过 ISO 50001 认证"等凭证，链上可即时验证、可吊销。
- 受信发证方注册表（Trust Anchor），分级（root → intermediate）。

**与谁协作**
- 给 `device` 提供"主体身份"的引用目标。
- 给 `eac / carbon / rwa / stablecoin` 提供"谁能发行""谁能持有""谁能 retire"的判断依据。
- 给 `policy / sanctions / mrv` 提供凭证查询接口。

---

#### 4.2 `device` —— 设备身份与远程证明

**解决什么**
绿证发行方必须确认"这度电真的来自这块光伏板""这条电表读数没被掉包"。设备如果没有可验证身份，所有上链数据都是无源之水。

**关键能力**
- 每台设备一份链上记录：设备 DID、归属主体、设备类型（电表 / 逆变器 / 充电桩 / 电池 / 传感器）、型号、序列号、固件哈希、地理位置、所属电网区。
- 远程证明（Remote Attestation）：基于 TEE / TPM 的固件度量值上链，状态由 `unverified` → `attested`。
- 设备 ↔ 主体双签绑定，防止偷换。
- 固件升级时必须重新证明，否则该设备的数据被自动标记为可疑。
- 吊销列表（CRL）+ 自动失效阈值。

**与谁协作**
- 所有 `meter` 上传读数必须带设备签名。
- `eac` 在 issue 阶段会校验"这条产电记录所对应的设备是否处于 attested 状态"。
- `dataslash` 在错报时罚没设备背后主体的 bond。

---

#### 4.3 `audit` —— 治理动作不可变日志

**解决什么**
治理变更（参数调整、白名单增删、强制冻结、紧急停机）必须留痕，且不可篡改、可由监管事后追查。

**关键能力**
- 结构化事件：事件类型、行为人、对象、动作、附加数据、区块高度、交易哈希。
- 事件 schema 自描述（schema URI），方便外部工具按版本解析。
- 严重程度分级（info / warn / critical），方便告警系统订阅。
- 真正实现保留期：到期日志按 Merkle root 锚定外部归档（IPFS / Filecoin / S3），链上只留摘要。
- 监管视图密钥：监管 DID 可被授权解密某一时间窗或某一对象的事件明文。

**与谁协作**
- 几乎所有写操作都会留痕到 `audit`。
- 与 `mrv` 协作生成定期合规报送包。

---

### 数据可信层

#### 4.4 `oracle` —— 多源喂价与外部事实聚合

**解决什么**
能源结算高度依赖外部事实：电价、汇率、碳市场拍卖价、天气预报、外部托管行储备金证明。任何单一来源都不可信，单点故障会让结算瘫痪。

**关键能力**
- **Topic 第一公民**：每个数据流都是命名 Topic，例如 `power.spot.PJM.WHUB`、`fx.EURUSD`、`carbon.EUA.dec25`、`reserve.usdc.attest`。
- **真正的多源聚合**：每个 Topic 配最低签名人数、最大数据年龄、离群剔除带宽，链上确定性算出中位数 / 加权均值 / TWAP。
- **共识级聚合**：关键 Topic 走 ABCI++ vote-extension，验证人在出块时同步签价格，避免"先到先得"被抢跑。
- **拉/推双模**：高频数据自动推送，低频按需拉取以节省 gas。
- **数据提供者强制 bond**：错报、过期、签名缺失由 `dataslash` 罚没。
- **储备金证明子接口**：托管行 M-of-N 多签 attestation 直接喂给 `stablecoin`。

**与谁协作**
- `meter` 的电价标记、`market` 的指数结算、`stablecoin` 的 PoR、`contract` 的 PPA 自动结算，全部依赖它。

---

#### 4.5 `meter` —— 计量数据上链

**解决什么**
"绿证"和"碳"的根都是一条条电表读数。读数必须设备签、可批量、可隐私、可在监管面前证明。

**关键能力**
- **计量点（Metering Point）注册表**：唯一编号、所属设备、所属主体、所属电网区、电网公司、计费方案、测量类型（有功 / 无功 / 电压 / 频率）、单位、时区。
- **读数记录**：测量周期（15 分钟 / 1 小时 / 1 天）、起止时间、值的承诺（Pedersen commitment，不暴露明文）、设备签名、数据质量标记。
- **批量上链**：默认 Merkle root + 索引前缀的批量校验，支持 100 TPS 以上的高频遥测。
- **隐私可选**：默认上承诺值，可针对公开数据（如总装机）开启明文模式；监管视图密钥可解。
- **流式上报**：与 `scheduler` 联动，设备一次授权后周期自动签，无需每次重签名。
- **可证溯源**：一条读数附带的 proof 可证明"设备已通过 attestation""归属主体已 KYC""计量点已注册"三件事。

**与谁协作**
- 给 `eac` 发证、`cfe247` 匹配、`market` 的实物交割、`mrv` 的合规报告提供基础数据。

---

### 资产层

#### 4.6 `eac` —— 通用能源属性证书

**解决什么**
"绿电属性"是全球能源结算的核心商品，但 GO（欧）/ I-REC / REC（美）/ GEC（中）/ LGC（澳）/ J-Credit（日）格式各异，跨平台流转必须线下确权。最大风险是"双重计数"——同一度电被卖了两次。

**关键能力**
- **统一类型**：一张证书 = 1 MWh，全局唯一编号，标准类型字段（IREC / EU_GO / US_REC / CN_GEC / AU_LGC / JP_J_CREDIT / NATIVE）。
- **小时级粒度**：起止时间精确到小时，支持 24/7 CFE 报告。
- **完整属性**：技术（光伏 / 风 / 水 / 核 / 生物质 / 地热 / 储能）、项目主体、设备、电网区、年份、外部注册表序列号。
- **三态机**：`Issued → Transferred → Retired`；retire 不可逆。
- **代理 retire**：可代他人 retire，记录受益方与用途（自愿 Scope 2 / 合规 / RGGI / Article 6 / 税收抵免）。
- **跨注册表桥接**：从外部注册表（I-REC、M-RETS、APX 等）锁定证书后链上 mint；链上 burn 后外部释放，由 `oracle` 储备金证明保证 1:1。
- **批量发行**：ERC-1155 风格，一笔交易发行同项目同时段的批量证书。

**与谁协作**
- `cfe247` 用它做 24/7 匹配；`market` 让它进入交易撮合；`rwa` 可以把绿证收益打包成证券型代币；`mrv` 引用它生成 Scope 2 报告。

---

#### 4.7 `carbon` —— 碳配额与碳抵消

**解决什么**
碳市场分两套：合规市场（EUA / CCA / RGGI / CCER）由政府发放配额；自愿市场（Verra / Gold Standard / ART / ACR）由项目签发抵消。两套都面临"不可见、不可验证、有重复计算"的老问题，且 Article 6.4 要求做"对应调整"（CA）以避免国家间双重计数。

**关键能力**
- **两类资产并存**：合规配额（Allowance）与自愿抵消（Offset）分开建模。
- **完整属性**：注册表、项目编号、方法学、年份、tCO₂e、CCP（Core Carbon Principle）标签、Article 6 对应调整状态。
- **Retire 即销毁**：retire 时同时铸造一张 retirement NFT 作为不可篡改的销毁证据。
- **池化（Pool）**：BCT/NCT 风格的同质化篮子，但带过滤属性（年份 ≥ X / 仅特定方法学 / 仅特定地理区）。
- **跨注册表桥**：双向桥到 Verra、Toucan、Klima、Article 6.4 等。
- **互斥规则**：与 `eac` 联动，防止同一度电既被算 RE 又被算 offset。

**与谁协作**
- `mrv` 引用它生成 Scope 1 / Scope 3 报告；`market` 把它做成期货标的；`clearing` 用它做净额结算。

---

#### 4.8 `cfe247` —— 24/7 无碳能源匹配

**解决什么**
传统的"年度 RE100"只要求"全年 1:1 匹配"，但实际上夜里用的电仍可能来自煤电。Google、UN-Energy 推动的 24/7 CFE Compact 要求**每小时**用同一电网区的可再生电匹配同小时的消耗。这件事链下做几乎不可行。

**关键能力**
- **消耗 attestation**：用户每小时消耗（kWh + 电网区）上链。
- **小时级匹配**：必须用同电网区、同小时、技术匹配的 EAC retire。
- **覆盖率指标**：链上自动计算 24/7 CFE 评分（hourly / annual / location-matched）。
- **报告输出**：直接产出符合 24/7 CFE Compact 与 EnergyTag 标准的可验证报告包。

**与谁协作**
- 严重依赖 `eac` 的小时级粒度；输出给 `mrv` 作为 Scope 2 报告输入。

---

#### 4.9 `rwa` —— 合规感知的资产通证

**解决什么**
PPA 收益权、储能资产份额、绿色债券、电站股权要上链，但持有人必须 KYC、必须满足司法辖区限制、必须支持锁仓 / 冻结 / 强制划转。普通 ERC-20 没有这些能力。

**关键能力**
- 兼容 ERC-3643 / ERC-1400 的合规通证标准。
- **转让前置策略（DSL）**：身份角色、必须持有的凭证（合格投资人、KYB 完成、FATCA W-8）、司法辖区白/黑名单、锁仓期、归属期、单地址持仓上限。
- **强制操作**：发行人可强制划转、冻结、回收（每次自动写 `audit`）。
- **现金流分发**：分红 / 票息按快照 push；支持稳定币派息。
- **赎回队列**：T+N 排队赎回，支持部分赎回。
- **快照 / 投票**：股权类资产可做股东大会快照与链上投票。

**与谁协作**
- 持仓资格走 `did` + `policy`；制裁过滤走 `sanctions`；分红派息和赎回对价走 `stablecoin`；交易撮合走 `market`。

---

#### 4.10 `stablecoin` —— 多币种合规稳定币

**解决什么**
能源结算必须以法币计价（5.9 元/绿证、85 €/MWh），链上没有合规稳定币就只能链下结算，链上属性失效一半。同时各国对发行人有牌照要求（美国 NYDFS、欧盟 MiCA、新加坡 PSA）。

**关键能力**
- **多币种独立**：USD / EUR / GBP / JPY / SGD / ... 各自独立合约空间。
- **发行人角色**：与 `did` 绑定，多签 mint authority。
- **储备金证明**：与 `oracle.reserve` 联动，按周期自动核对储备真实性。
- **合规字段**：blacklist、freeze、Travel Rule（FATF）字段透传。
- **配额制**：每个发行人有 mint/burn 上限，可治理调整。
- **赎回**：链下法币兑付走 `escrow`。

**与谁协作**
- `rwa` 的派息对价；`market` 的撮合对价；`clearing` 的最终结算货币。

---

### 市场层

#### 4.11 `market` —— 现货与衍生品撮合引擎

**解决什么**
电力市场需要现货（日前 / 实时）、中长期（PPA / 期货 / 期权 / 价差合约）多种工具。普通智能合约可以做撮合，但电力出清要求"块边界原子性"——不能让某些订单被夹在前面提价。

**关键能力**
- **品种**：现货 kWh、日前、日内、期货、CFD、互换、期权（PPA 标的）。
- **双轨撮合**：
  - 连续订单簿——处理高频小额订单。
  - **Frequent Batch Auction（FBA）**——每若干区块一次统一出清拍卖，结构性消除抢跑，电力市场首选。
- **保证金体系**：每品种独立的初始保证金 / 维持保证金，用 `rwa` 的合格抵押品锁定。
- **持仓引擎**：净持仓、PnL、强平点。
- **风控开关**：日内涨跌幅限制、熔断、单户持仓上限。
- **结算**：撮合即调用 `clearing` 做原子 DvP。

**与谁协作**
- 标的来自 `eac / carbon / rwa`；对价来自 `stablecoin`；最终结算交给 `clearing`。

---

#### 4.12 `auction` —— 通用拍卖原子

**解决什么**
能源场景里大量"集中竞价"事件：政府对配额的初始拍卖、容量市场拍卖、可再生能源招标、绿证年度集中竞价。每一次都自己写一遍合约不现实。

**关键能力**
- **多种模式**：英式 / 荷式 / 密封竞价 / 集合竞价 / 多单元统一价 / 出价即支付。
- **场景复用**：容量市场、配额初始拍卖、可再生能源招标、年度集中竞价都共用同一原语。
- **开标即结算**：开标完成自动调 `clearing`，无需事后再撮一次。

**与谁协作**
- 标的与对价同 `market`；治理事件走 `audit`。

---

#### 4.13 `contract` —— 双边合同仓

**解决什么**
PPA、VPPA（虚拟 PPA）、Tolling、CfD、Sleeved PPA 这些双边合同长期是 PDF + 邮件交付，结算靠人工对账，争议解决慢。

**关键能力**
- **合同状态机**：起草 → 签署 → 生效 → 周期结算 → 终止 / 续约。
- **结算计划**：cron + 引用 `oracle` 价格指数 → 自动结算。
- **争议挂起**：进入 `dispute` 模块，结算暂停。
- **合同模板**：链上存 schema URI（IPFS） + 哈希存证；签章走 `did` 多签。

**与谁协作**
- 价格来自 `oracle`；交割资产来自 `eac` / 实物；对价来自 `stablecoin`；争议进 `dispute`。

---

### 结算与支付层

#### 4.14 `clearing` —— 多边净额清算

**解决什么**
"一手交钱一手交证"是能源结算最核心的诉求。如果资产移交、对价支付、绿证 retire 不能原子完成，就一定会有人钻"中间状态"的空子。

**关键能力**
- **DvP / DvD**：资产 ↔ 对价 ↔ 绿证 retire / 碳 retire，三者在同一笔交易内原子完成或全部回滚。
- **多边净额**：日内多笔反向交易先做净额计算，再单笔结算，节省 gas 与对价占用。
- **可选 CCP（中央对手方）**：在持牌场景下做合约更替。
- **违约瀑布**：违约保证金 → 默认基金 → 共担。

**与谁协作**
- 上游接 `market` / `auction` / `contract`；下游消费 `eac / carbon / rwa / stablecoin` 余额。

---

#### 4.15 `escrow` —— 多签托管

**解决什么**
跨境结算、纠纷资金保留、阶段性付款都需要"暂存于第三方"，但传统托管账户体验差、对账慢。

**关键能力**
- 时间锁、多 oracle 触发、人工仲裁触发、分期释放。
- 与 `dispute` 联动，争议期间资金锁定。

**与谁协作**
- 主要服务于 `contract` 与 `stablecoin` 的赎回流。

---

#### 4.16 `streampay` —— 流式支付

**解决什么**
电动车充电、V2G 反向放电、算力按秒计费、订阅式电力服务，每一笔都发交易成本太高。需要"开闸放水"式的连续付费。

**关键能力**
- Sablier / Superfluid 风格的连续流（per-second 计算）。
- gas 摊销：链上累计、链下读取，提取 / 暂停时再上链。
- 支持暂停、加速、终止、转让流权。
- V2G 场景：充电桩按 kWh 流式计费，结算时再走链上。

**与谁协作**
- 对价来自 `stablecoin`；接入设备走 `device`。

---

#### 4.17 `scheduler` —— 链上 Cron

**解决什么**
智能电表每 15 分钟一次上传，PPA 每月一次结算，PoR 每周一次校验——这些"周期性自动动作"如果都靠链下程序触发，就有单点故障与运维负担。

**关键能力**
- 周期性 msg 自动执行：一次签名 → 永续触发；可吊销、可暂停。
- 用 fee-pool 预付 gas，避免账户余额耗尽。
- 与 `meter` / `contract` / `oracle` / `stablecoin` 全面联动。

**与谁协作**
- 几乎所有需要"周期性触发"的模块。

---

### 合规与治理层

#### 4.18 `policy` —— 通证转让策略 DSL

**解决什么**
不同司法辖区对"谁能持有""谁能交易""锁仓多久"的要求各异。把这些规则硬编码进 `rwa` 或 `stablecoin` 不可维护。

**关键能力**
- 一组可组合的判断式：是否合格投资人、是否在白名单辖区、是否未被制裁、是否过了锁仓期、单户持仓是否超限。
- 策略可挂载到任一资产合约，通过治理升级。
- 每次校验失败有明确错误码，便于客户端处理。

**与谁协作**
- 被 `rwa` / `stablecoin` / 部分 `eac` 引用；查询 `did` 凭证。

---

#### 4.19 `sanctions` —— 全球制裁名单

**解决什么**
任何合规资产都必须做制裁过滤（OFAC、EU、UN、各国央行）。每个项目自己同步名单工作量巨大且容易漏。

**关键能力**
- 同步多个权威来源的制裁名单（oracle pull + 治理确认）。
- 命中即冻结相关地址在 `rwa` 与 `stablecoin` 的余额。
- 历史命中可追溯，不可逆删除（合规审计需要）。

**与谁协作**
- 被 `policy` 调用；冻结操作触发 `audit`。

---

#### 4.20 `mrv` —— 监测、报告、核证

**解决什么**
能源企业必须定期向监管 / ESG 投资人 / 客户提交合规报告：碳排放、Scope 2、24/7 CFE 覆盖率、绿证 retire 总量。链下手工汇总耗时长且容易出错。

**关键能力**
- 报告 schema 注册：按司法辖区 × 资产类型 × 时间窗。
- 自动汇总：从 `meter` / `eac` / `carbon` / `cfe247` 取数 → 按 schema 组装 → 用 VC 包装签名。
- 监管 DID 视图密钥解密敏感字段。
- 输出格式：JSON-LD（W3C）/ XBRL（财务报送）/ EnergyTag granular cert 包。
- 第三方核证机构注册表（Verifier registry）。

**与谁协作**
- 数据来自 `meter / eac / carbon / cfe247`；监管授权来自 `did`；报告本身留痕到 `audit`。

---

#### 4.21 `dispute` —— 数据与合同争议

**解决什么**
错报数据、合同结算金额异议、跨境交付纠纷需要一个链上仲裁流程，否则就要回到法院诉讼，时间成本太高。

**关键能力**
- 异议者质押 bond → 公开期 → 链上仲裁庭裁决 → 错方 bond 罚没。
- 仲裁庭成员资格由 `did` + VC 校验（必须持有"仲裁员"凭证）。
- 与 `oracle / meter / contract` 联动：争议期间相关结算暂停。

**与谁协作**
- 仲裁结果写入 `audit`；罚没动作走 `dataslash`。

---

#### 4.22 `dataslash` —— 数据提供者罚没

**解决什么**
共识层的 `staking.slashing` 只惩罚"出双签 / 长时间下线"等共识违规。但数据提供者上传假电表读数、假储备金证明，这类行为现有机制无法惩罚。

**关键能力**
- Oracle / 计量 / 桥接公证人必须独立 bond，与共识 stake 解耦。
- 错报、过期、签名缺失自动罚没；恶意行为由 `dispute` 触发罚没。
- 临时 jail（暂停接受其数据）+ 永久 ban。

**与谁协作**
- 监督对象：`oracle` / `meter` / 桥接节点；触发源：链上自动检测 + `dispute` 仲裁结果。

---

### 跨链与互操作

EnergyChain 不是孤岛：

- **IBC**：与 Cosmos 生态的其他能源 / 金融链直接互通。
- **EVM 桥**：到 Ethereum / Polygon 的 light-client + 门限签名桥，主要用途是与 Toucan / KlimaDAO / Verra 链上版本互操作。
- **外部注册表适配器**：I-REC、M-RETS、PJM-EIS、APX、Argus、Platts —— 走 `oracle` 的"M-of-N 公证人签名"模式，不直接持有外部 API key。
- **Article 6.4 桥**：与 UNFCCC 注册表对接，对应调整（CA）状态自动透传。

## 5. 十条通用设计原则

| # | 原则 | 落地表现 |
|---|---|---|
| 1 | **资产唯一性** | 一张 EAC = 1 MWh，全局序列号，retire 不可逆 —— 结构性杜绝双重计数 |
| 2 | **身份贯通三层** | 主体（DID）→ 设备（Device-DID）→ 计量点（MP），证书链可验证 |
| 3 | **结算原子性** | 资产 / 对价 / 绿证 retire 在同一笔交易中完成或全部回滚 |
| 4 | **可监管的隐私** | 默认上承诺值，监管节点持视图密钥可解明文 |
| 5 | **EVM 优先** | 每个原生模块都配 EVM precompile，Solidity 合约一等公民 |
| 6 | **数据可罚没** | 数据提供者独立 bond，错报罚没，与共识 slashing 解耦 |
| 7 | **可治理参数** | 限速、白名单、最大数据大小、保留期等全部可治理升级 |
| 8 | **标准对齐而非重造** | ERC-3643 / W3C VC / EN 16325 / Article 6.4 等已有标准优先采用 |
| 9 | **司法辖区参数化** | 不硬编码任何国家/地区规则，policy DSL 中作为参数传入 |
| 10 | **链下重账本，链上重证据** | 大体积数据归档到 IPFS / Filecoin / S3，链上只锚 Merkle root |

## 7. 分阶段路线图

| 阶段 | 目标 | 涉及模块 | 里程碑 |
|---|---|---|---|
| **M1 · 地基** | 数据可信层闭环 | `did` / `device` / `meter` / `oracle`（含聚合）/ `audit` | 测试网开放，设备签名 → 聚合 → 上链全链路打通 |
| **M2 · 资产化** | 链上发行可流转的能源资产 | `eac` / `carbon` / `cfe247` / `rwa` / `stablecoin` / `policy` / `sanctions` | 一张完整 EAC 从 issue → transfer → retire；24/7 CFE 报告可生成 |
| **M3 · 市场化** | 实现原子结算与 PPA 自动化 | `market` / `auction` / `contract` / `clearing` / `escrow` / `streampay` / `scheduler` | 第一笔 PPA 链上自动结算；现货 FBA 出清跑通 |
| **M4 · 合规与互联** | 监管报送 + 跨链 + 仲裁 | `mrv` / `dispute` / `dataslash` / EVM 桥 / 外部注册表适配器 | 与 Verra / Toucan / I-REC 双向桥接通；监管节点可解视图 |

每个阶段结束都要做：

1. 安全审计（核心模块外部审计）。
2. 经济模型评审（gas 经济、bond 大小、罚没比例）。
3. 标准合规自查（对照本文第 6 节）。

## 8. 与现有模块的关系

当前仓库里 `chain/x/` 下的四个模块（`energy / oracle / identity / audit`）属于早期 PoC：

| 旧模块 | 新设计中的去向 | 处置 |
|---|---|---|
| `energy` | 拆分为 `meter`（计量数据）+ `eac`（资产化）+ `cfe247`（小时匹配） | 完全替换 |
| `oracle` | 升级为聚合 + 储备金证明 + Topic 第一公民 | 重写 |
| `identity` | 升级为 `did`（主体）+ `device`（设备） | 替换并扩字段 |
| `audit` | 增 schema URI / 严重程度 / 监管视图密钥 / 真正实现保留期 | 演进式重构 |

迁移策略：旧链状态导出到 genesis → 新链以 schema-V2 启动；旧的 `EnergyData` 哈希记录可批量映射成新 `meter.Reading` 的"legacy"层级，不丢历史。

## 9. 名词表

| 术语 | 含义 |
|---|---|
| **EAC** | Energy Attribute Certificate，能源属性证书的统称。GO / I-REC / REC / GEC / LGC / J-Credit 都是其子类 |
| **GO** | Guarantee of Origin，欧盟 EN 16325 标准下的可再生电属性证书 |
| **I-REC** | International REC Standard，全球通用的可再生能源属性证书 |
| **REC** | Renewable Energy Certificate，北美体系（PJM-GATS、M-RETS 等） |
| **GEC** | Green Electricity Certificate，中国绿证 |
| **PPA** | Power Purchase Agreement，购电协议；VPPA 为虚拟 PPA |
| **CfD** | Contract for Difference，差价合约 |
| **CCER** | China Certified Emission Reduction，中国核证自愿减排量 |
| **VCS** | Verified Carbon Standard，由 Verra 维护的自愿碳标准 |
| **Article 6.4** | 巴黎协定 6.4 条机制下的国际转让减排成果（ITMO）框架 |
| **CA** | Corresponding Adjustment，对应调整，避免国家间双重计数 |
| **24/7 CFE** | 24/7 Carbon-Free Energy，要求每小时用同电网区可再生电匹配同小时消耗 |
| **DvP** | Delivery vs Payment，券款对付（资产与对价原子结算） |
| **DvD** | Delivery vs Delivery，券券对付（资产与资产原子互换） |
| **FBA** | Frequent Batch Auction，频繁批量拍卖，反抢跑撮合机制 |
| **PoR** | Proof of Reserve，储备金证明 |
| **VC** | Verifiable Credential，W3C 可验证凭证 |
| **DID** | Decentralized Identifier，W3C 去中心化身份标识 |
| **MRV** | Monitoring / Reporting / Verification，监测、报告、核证 |
| **TEE** | Trusted Execution Environment，可信执行环境（SGX / TDX 等） |
| **Bond** | 数据提供者 / 仲裁员 / 桥节点必须缴纳的可罚没保证金 |
